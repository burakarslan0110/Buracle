# Parallel agents: the lane protocol

The always-loaded *Parallel agents* rule holds the core. Read this file before you launch lanes. Every workflow names its lanes in its skill; this is the protocol they share on every harness. You are the lead.

- **A lane is a part you can hand over and check on its own:** one plan task, one research angle, one hypothesis to refute, one entry point to trace, one criterion to judge, one review. Parts that share files or need each other's results stay in one lane, in order.
- **Fan out when it pays.** Launch lanes when there are at least 2 independent parts, each needs more than a few tool calls, and their write sets do not overlap. Launch them all at once, in the background where the harness allows, then work on what no lane owns. No lane for a lookup you can do in one call.
- **Read-only lanes** explore, trace, refute, judge or review; they need no worktree. **Editing lanes:** when 2 or more run at the same time, each gets its own worktree from `buracle worktree create <slug>-<n>` (it also sets `worktree: true` on the plan: when the run is not in a worktree, undo that with `buracle plan set worktree false`). A single editing lane may work in your tree while you do not edit.
- **No worktree, no parallel editing lane.** When editing lanes run at the same time and one lane's worktree cannot be created, that lane does not start: run its tasks yourself, in order, or report the blocker; never run it in the shared checkout next to another editor. A lane briefed to work in its own worktree that finds itself in the shared checkout stops and reports `blocked`.
- **Brief each lane as a peer**, because it does not see your conversation: the goal; the inputs (task text, files, facts already known, what is ruled out); one line of tool routing (codegraph and semble with the project root, `rg`, context7 for library APIs); read-only or the paths it may write; what it must not touch (the plan or run file, memory writes, other lanes' files, git history); the budget; and the report: status (`done`, `blocked` or `no_progress`), a summary, and evidence as claim plus `path:line` or command → result, in at most about 400 words that point at files and lines instead of pasting code, diffs or logs.
- **You integrate and verify.** A lane's report is a lead, not evidence: check 2 of its claims yourself and read every diff. Merge editing lanes in dependency order (`git merge --squash <branch>` in your checkout, then `git commit`; recipes in the `buracle` skill) and run the checks after every merge. Only you tick plan boxes and write the plan or run file.
- **Decisions stay with you.** A lane never asks the user, never runs a `buracle plan` or `buracle flow` command that changes state (plan pause, resume, set, complete, verify, register, unregister; flow start, phase, end), and never approves a plan, a merge or a sign-off. It returns `blocked` with the question and its options, and you ask the user.
- **Limits.** At most about 4 lanes at once. Run `buracle usage --json` before 3 or more lanes and narrow the fan-out when a window is nearly used up. Stop a lane that reports no progress twice. Lanes never start lanes: when you are a lane yourself, or the harness has no agent tool, do the same lanes yourself, in order, with the same reports.
- **Per harness.** Claude Code: the `Agent` tool, one call per lane in a single message, and never with a `name`: while agent teams are on, a named call starts a teammate instead of a subagent, and a teammate's report arrives late, in pieces and twice. Buracle Stack's lanes are background subagents, never an agent team; each result arrives once, when the lane ends. Continue a finished lane with `SendMessage` to the agent ID its launch returned, and stop one with `TaskStop`. Read-only lanes can use the `Explore` agent type, which cannot be continued. Codex: `spawn_agent`, then `wait_agent` and `close_agent`; a Codex subagent gets no routing note, so the routing line in the brief is required. OpenCode: the `subagent` tool, in the background for long lanes. Oh My Pi: one `task` call with one batch item per lane. Buracle Stack's review agents (plan-build-review, goal-build-review, changes-review) exist on all four.

## Stopping what you launched

- A stop or cancel also covers what this session launched: stop its running lanes and background commands too. Claude Code: `TaskStop`. Codex: `close_agent` for subagents; ask the user to run `/stop` for background terminals (`/ps` lists them). OpenCode: you cannot cancel a background subagent or shell command yourself, so ask the user to stop it in the TUI: select it in the subagent or shell list and press ctrl+d (Interrupt subagent, Kill shell command). Oh My Pi: `write proc://<id>/kill`. Check what this session started; a list of other sessions does not prove that nothing runs. If you cannot stop something, name the exact command or key and wait.
