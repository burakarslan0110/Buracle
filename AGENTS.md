# Buracle: repository guide for coding agents

Buracle: everything your coding agents need, in one place. One canonical set of skills, rules,
agents, MCP servers, hooks and status lines, generated for Claude Code, Codex CLI, OpenCode (v2) and
Oh My Pi.
TypeScript on Bun ≥ 1.4, ESM only, strict TypeScript.

## Read first

- `docs/` is not committed (`.gitignore`): the design, the contracts, the usage guide and the
  generated reference live on the author's machine. On a clone without it, the code and the tests
  are the reference; the doc lint skips what is missing, and `buracle build` still writes
  `docs/reference/` locally without recording it in the manifest or checking it.
- `docs/dev/CONTRACTS.md` is **binding** for code: types, file layout, ownership. It holds §0–§4 and
  §9–§12 and an index of every section; `docs/dev/contracts/core.md` (§5 core API),
  `engine.md` (§6–§7 engine, data files) and `adapters.md` (§8 adapters) are binding too. A
  "CONTRACTS §n" citation is found through that index. If the contract disagrees with anything
  else, it wins; report the disagreement instead of working around it.
- `docs/DESIGN.md` is the user-facing design. Its §4 (harness adapters), §7 (memory) and §11 (MCP
  servers, plugins and skills) live in `docs/design/` with the same section numbers; a "DESIGN §n.m"
  citation is found through the index DESIGN.md keeps in place of each.

## Layout

```
canonical/          single source of truth (YAML data + English prose: rules, skills, agents);
                    skill-triggers.yaml = the skill router's trigger phrases (data, any language);
                    notices.yaml = one-time release notices (H17), shown once per machine
src/core/           PURE logic (copied verbatim into the Claude plugin)
  flow/             workflow progress: phase catalog, flow record, the band view model
  workspace.ts      index exclusions, index states, the H21 workspace context line
  effort.ts         reasoning-effort levels per harness (maps `effort.*` to the level adapters write)
  context-mode*.ts  Context Mode (the context-mode MCP server): the tools Buracle allows and hides,
                    the session bridge's event normalizers (redacted, capped) and, in
                    context-mode-restore.ts, the restore text (H27); its guards are policy/sandbox.ts
src/engine/         IO: paths, fsx, proc, git, log, config loader, canonical loader, txn, merge, diff
  context-mode.ts   Context Mode's storage roots (one per harness and project under
                    $BURACLE_HOME/context-mode), its toolchain copy and its server's environment
src/cli/main.ts     thin entry only (never import it); the router lives in src/cli/router.ts; one module per command in src/cli/commands/<name>.ts
src/adapters/<h>/   per-harness generator, runtime templates and hook handlers; registry.ts
src/adapters/shared/context-mode/  Context Mode's session bridge over context-mode's own session
                    library: the `buracle ctx session` ops, the Claude/Codex bridge, the child client,
                    the stats reader, H16 housekeeping and the smoke test (the OpenCode server
                    plugin and the omp extension never bundle session.ts, library.ts or bridge.ts;
                    build tests pin it)
src/workflow/       plan, flow, worktree, review-scope, notify, project, skills/rules lint, session-store
                    (session state, telemetry, session resolution, aliases), usage ledger, code indexes (H21);
                    plan-audit (the plan against the diff), worktree-branch, plan-capture (H12),
                    plan-review and plan-lanes (review records, plan lanes), plan-native, plan-notes
                    and review-notes (the review page's notes), companion* (the second opinion),
                    project-assets/-check/-adopt (H28), non-project.ts (the one 'never a project' rule)
src/memory/         the memory on CortexDB: client (cortex.ts), store (one file per project + person.db),
                    MCP server, CLI twins, session start text, finalizer, sweep and upkeep, profile,
                    handoffs, distillation, the old vault's import, doctor, the harness choice for its
                    model calls (model.ts), the built-in embedder (embed.ts), the tick (tick.ts), what the sweep settles without a model (settle.ts), the files it finds by name (sources.ts),
                    and backups, restore, export and import (backup.ts, export.ts)
  ui/               the web UI: the brain, the review page, sessions and usage, notifications and the
                    workflow switches; its JSON API and event stream, and the pages' hand-written JS and CSS
src/usage/          per-harness usage collectors
harness/<h>/        GENERATED by `buracle build` and committed; never edit by hand
harness/hook-data.json  GENERATED too (listed in harness/.manifest.json): the part of canonical/ the
                    Claude and Codex command hooks read (src/cli/hook-data.ts); a canonical/ edit
                    reaches them after `buracle build`
tests/              bun tests mirroring src/ (fixtures in tests/fixtures/<area>/)
```

## Commands

```sh
bun install                      # exact-pinned deps from bun.lock
bun test                         # all tests (bunfig.toml: root=tests, preload sandboxes HOME)
bun test --timeout 60000         # the same on Windows, where starting a process is slow (CI does this)
bun test tests/engine/txn.test.ts
bunx tsc --noEmit -p .           # must stay clean for the whole repo
bun src/cli/main.ts --help       # the CLI runs straight from source, no build step
```

Every `bun src/cli/main.ts …` run (`build` included) refreshes `$BURACLE_HOME/state/runtime-config.json`,
which the installed harnesses read. While developing, run it with `HOME` and `BURACLE_HOME` pointing
at a temp dir (the generated output does not depend on them):
`T=$(mktemp -d) && HOME=$T BURACLE_HOME=$T/.buracle bun src/cli/main.ts build`.

The installed hooks run a frozen copy of the checkout (`$BURACLE_HOME/runtime/<id>`,
src/engine/update/runtime.ts), and OpenCode runs a copy of its plugin: a checkout edit reaches them
only after `buracle install`. The Claude plugin's mod and the omp extension load `harness/` in place
(after `/reload-plugins` or a new omp session).

Release checks (run all three before every commit; GitHub Actions runs the same three on every
push to a branch other than `main`, on macOS arm64, Linux x64 and Windows x64, with the Bun in
`.bun-version`, and every job has to pass):

```sh
bunx tsc --noEmit -p .                                                   # clean
T=$(mktemp -d) && HOME=$T BURACLE_HOME=$T/.buracle bun src/cli/main.ts build --check   # no drift
bun test                                                                 # 0 fail
```

Branches and releases: work lands on `dev`, and `main` holds only released files. When every job
passes on a push to `dev` and the released files changed, the `release` job in
`.github/workflows/ci.yml` picks the version by itself: the next patch after the newest
`v<major.minor>.*` tag, or the version in `package.json` while that version has no release (raise
major or minor there to start a new line). It rebuilds the commit at that version (`harness/`
carries it), leaves out `RELEASE_DROPS` (`tests/` and `bunfig.toml`), writes the result to `main` as
one commit per release and publishes `v<version>` from it with `scripts/install.sh` and
`scripts/install.ps1` attached. A push that changes only the test suite releases nothing. The
`windows-install` job installs the tree without `RELEASE_DROPS` before. CI never runs on `main`. The
install scripts clone `main`, so installs and `buracle update` (which follows the checkout's
upstream) get exactly the released files.

`build --check` and `tests/cli/ops/repo-drift.test.ts` fail after a Bun upgrade until the OpenCode
and omp bundles are rebuilt (sandboxed `build`) and committed together with the new version in
`.bun-version` (CI installs that Bun). The real-binary smoke tests
(`tests/adapters/*/smoke.test.ts`, `tests/adapters/claude-mod/claude-cli.test.ts`) run inside
`bun test` when the harness is installed; move a tested version in `src/engine/update/tested-with.ts`
only after they pass on it. The Codex and OpenCode smoke tests also probe the host limits recorded in
`src/adapters/shared/host-limits.ts`: a `probeMisses` failure means a probe no longer reads what it
should, a `canNowBeClosed` one that the newer host can close that limit. Either way, update the record,
the FEATURES matrix in `tests/adapters/parity.test.ts` and the host-limits table in
`docs/design/harness-adapters.md` together, and raise a limit's `checkedOn` after re-probing.

## Rules

- **Sources.** Work only from official harness docs/sources and local `--help` output. Write
  everything in your own words.
- **Ownership.** Each task owns specific paths (CONTRACTS §11). Change only what your task owns;
  ask for other changes in your report.
- **Generation.** Edit `canonical/` and `src/`, then run `buracle build`. Generated output must be
  deterministic (no timestamps, stable key order); `buracle build --check` fails on any drift.
- **Pure core.** `src/core/**` uses relative imports only: no `node:*`, `bun:*`, npm packages,
  `process`, `Bun`, timers, `Date.now()` or `Math.random()`. Time and randomness are parameters.
  It must type-check with `target es2023`, `strict`, `noUncheckedIndexedAccess`,
  `moduleResolution bundler`, `jsx react` + `jsxFactory h`. `tests/core/purity.test.ts` enforces this.
- **Writes to harness dirs** go through the transaction engine (`src/engine/txn.ts`): backups,
  journal, verification and automatic rollback. Never overwrite a file that does not parse; never
  overwrite a value the user changed (the ownership ledger decides), except keys a plan marks
  `enforce` (the harnesses' no-approval keys while `permissions.enforce` is on, and the Claude Code
  env keys in `~/.claude/settings.json`): Buracle writes them
  again with a warning, records the value it displaced and restores it on uninstall. Keys a plan
  marks `soft` (the default reasoning effort) keep a value the user changed and report it as
  skipped, never as a conflict. A value that already equaled Buracle's when first recorded is
  `adopted`: it stays the user's (never overwritten, never removed). Dangling symlinks are never
  written through; a file rewritten by someone else while a transaction runs aborts it; a
  transaction left `applying` by a killed process is rolled back by the next
  `applyPlans`/`rollbackTxn`. Paths come from
  `src/engine/paths.ts` only (it honors `HOME`, `BURACLE_HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`,
  `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `PI_CODING_AGENT_DIR`). A command a shell
  runs to reach the shim uses `"${BURACLE_HOME:-$HOME/.buracle}/bin/buracle"`; where a harness
  config cannot expand variables, the install step writes the expanded absolute path
  (CONTRACTS §2, I8).
- **Hooks fail open** (except deliberate guards) and never print logs to stdout; log with
  `src/engine/log.ts`. The dispatcher diverts any stray stdout output of a handler to the log.
  Claude Code's and Codex's PreToolUse fail closed: when the hook cannot load or decide, the shim
  and `src/engine/hook-fail.ts` answer with a denial that names `buracle doctor`.
- **Dependencies.** Runtime: `yaml@2.9.1`, `jsonc-parser@3.3.1`. Dev: `typescript@6.0.3`,
  `@types/bun@1.4.2`. Bun built-ins are fine outside `src/core`. Add nothing else.
- **Language.** Everything is English: code, comments, identifiers, test names, agent-facing prose
  (skills, rules, agents, hook texts), user docs, CLI output, status lines, the mod and the web UI.
  The one exception is category D, the recognition of text in the user's language (intents,
  consent and approval phrases, routine questions, receipt claims, memory query stopwords,
  secret-word redaction, case folding, the skill router's trigger phrases, and the plan validator's
  vague-filler phrases, since plan prose follows the user's language): its Turkish words stay as
  matching data, behind English identifiers and English comments. The brain web UI is English
  only (one dictionary in `src/memory/ui/i18n.js`, no language switch). Agents reply in the language the
  user writes in. The one Turkish document is `README.tr.md`, a translation of `README.md` kept in
  step with it (the doc lint does not scan it).

## Tests

- Files are `tests/**/*.test.ts`. Use `withSandbox()` from `tests/helpers/sandbox.ts` for anything
  that touches the filesystem: it points `HOME`/`BURACLE_HOME` at a temp dir and clears harness
  overrides.
- Tests must never touch the real `~/.claude`, `~/.codex`, `~/.config/opencode`, `~/.omp`,
  `~/.agents`, `~/.buracle` (the brain included) or `~/Documents/Buracle` (the old memory vault).
  The preload fingerprints them before the run and `tests/zz-real-home-untouched.test.ts` checks
  them afterwards.
- Memory tests run on the fake CortexDB in `tests/fixtures/cortexdb/` (the preload points
  `BURACLE_CORTEXDB_BIN` at it); never download or run the real binary in a test. A run against the
  real binary sets `BURACLE_CORTEXDB_SMOKE=<path to cortexdb-mcp>`.
- `Bun.spawn`/`Bun.spawnSync` without `env` run the child with the environment the process started
  with (the real `HOME` in tests, because the preload sandboxes `HOME` through `process.env`): always
  pass `env: { ...process.env }`; `tests/engine/spawn-env.test.ts` enforces it under `src/`.
- Fault injection: `BURACLE_TXN_FAIL_AT=<n>` makes the n-th transaction write throw;
  `txnTestHooks` (txn.ts) simulates another process touching files mid-transaction.
- Claude mod tests live in `harness/claude/tests/` and run with `claude plugin test harness/claude`.
- Context Mode tests use the fixture package in `tests/fixtures/context-mode/` (stub session-library
  modules), never the real package, and never run context-mode code against the real home. The
  opt-in tests against a real installed package run only with
  `BURACLE_CM_SMOKE=<context-mode package folder> bun test tests/adapters/shared/context-mode-maint.test.ts tests/adapters/codex/context-mode.test.ts -t OPT-IN`:
  they drive Buracle's CLI and hooks in child processes whose HOME, BURACLE_HOME, CLAUDE_CONFIG_DIR,
  CODEX_HOME, XDG_*, TMPDIR and CONTEXT_MODE_DIR point into a temp folder.
- `docs/` is not in the public repository (it is gitignored), so a test reads a file under `docs/`
  only behind a guard (`HAS_DOCS`, as in `tests/workflow/doc-lint.test.ts` and
  `tests/adapters/parity.test.ts`); CI runs without it.
- The preload sets the quiet switches (`BURACLE_NO_NOTIFY`, `BURACLE_NO_NOTICES` and the others in
  `TEST_DEFAULT_ENV`); a test of that behavior unsets one with `withEnv`.
- `tests/workflow/doc-lint.test.ts` keeps the user docs, the design (`docs/DESIGN.md`, `docs/design/`) and the contract English,
  their links, anchors and the repository paths they name valid, and the contract's section index
  complete.
- `tests/workflow/language-guard.test.ts` keeps canonical/, src/ and the generated harness/ (JS
  bundles decoded, each line charged to its source module) English outside category D; a new file
  that holds category D data needs an entry, with its reason, in that test's allowlist.
